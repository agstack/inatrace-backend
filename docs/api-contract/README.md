# OpenAPI contract baseline

`openapi.json` is the reviewed, canonical OpenAPI document generated by the
running backend. It is a contract-review input, not a hand-maintained API
description.

Normal backend tests export the current document to `target/api-contract/` and
fail if its canonical bytes differ from this file. The target directory also
contains `manifest.json`, whose hash is verified against the exported bytes.
It records the producer repository and revision, Java runtime, the springdoc
version read from `pom.xml`, and the normalization format version.

The root-level OpenAPI `servers` value is intentionally excluded from the
canonical comparison: it is generated deployment metadata, not a frontend API
contract change. All other fields, including operation IDs, request/response
schemas, media types, enums and required properties, remain in the baseline.

An artifact created from a dirty working tree carries `source_tree_digest`.
It is SHA-256 over the binary tracked diff from `HEAD` plus the sorted paths
and content hashes of untracked files. A clean CI artifact intentionally has
no such field. This makes a local, dirty export traceable without presenting it
as an artifact of the named commit.

To intentionally update the baseline after reviewing an API change, run:

```bash
mvn -q -DargLine=-Dapi.version=1.43 -Dtest=OpenApiContractTest -Dapi.contract.update=true test
```

Review the resulting `openapi.json` diff, identify affected frontend and mobile
consumers, and include that compatibility evidence in the change. Do not use
the update flag in CI.

## CI artifact and consumers

The backend CI workflow uploads `target/api-contract/` as `api-contract-v1`
for 14 days. Retrieve it from the exact workflow run and attempt associated
with the reviewed backend revision; do not treat an artifact with a different
`source_revision`, `spec_sha256` or `normalization_version` as interchangeable.

The producer validates its own manifest and specification. The Angular consumer
validation is deliberately separate work (frontend issue #31): it must accept a
pinned, offline `openapi.json` plus `manifest.json`, reject invalid hashes or
versions, and generate/review its client without depending on a moving backend
`main`. Mobile consumers are not regenerated by this backend check; an accepted
API change still requires their compatibility review.

Merge order is therefore: review and merge the backend contract baseline first;
then have the frontend consume the exact published artifact; finally merge the
frontend client change with its recorded manifest/revision. The runtime matrix
below remains complementary to the OpenAPI shape comparison.

## Runtime contract matrix

The OpenAPI baseline detects documented-shape changes. These integration tests
exercise representative runtime responses and are required evidence when a
related contract changes:

| Surface | Existing evidence | Pinned behaviour |
| --- | --- | --- |
| Session validation error | `ApiErrorResponseIntegrationTest#validationErrorsDefaultToJsonWhenAcceptHeaderIsMissing` | JSON content type, stable error status and validation fields |
| Paginated farmer list | `FarmerAndPlotApiTest#ownCompanyFarmerListIsReadable` | authenticated JSON list scoped to its company, with `limit`/`offset` |
| Plot list | `FarmerAndPlotApiTest#ownCompanyPlotsAreReadable` | JSON envelope and plot name, GeoID and coordinates fields |
| Payment response | `PaymentApiAuthTest#paymentAndBulkPaymentByIdAreTenantScoped` | authenticated JSON data stays tenant-scoped |
| Processing response | `ProcessingActionApiAuthTest#processingActionReadsAreTenantScoped` | authenticated processing-action JSON remains tenant-scoped |
| Public label | `PublicLabelApiTest#publishedLabelIsAnonymousButDraftLandingAndFeedbackCreationAreWithdrawn` | public published-label data remains readable; drafts remain withheld |

This is not a replacement for consumer tests or end-to-end flows. It identifies
the focused runtime tests to extend whenever a baseline diff affects one of
these areas.
